01 Product Overview

Axia is a security-event analysis platform. It ingests events from data sources (Microsoft 365 / Outlook, Microsoft Purview DLP, Cursor and other webhook sources, API), enriches and classifies them, detects sensitive-data exposure with an LLM, and surfaces cases in a web dashboard. Integration setup for Microsoft Purview and Cursor is in §8.

Hosts

The full product runs across two EC2 instances, each with its own docker-compose file that communicate over private-IP URLs.

02 Prerequisites

Axia-side dependencies

Container images are stored in Axia's AWS ECR and are pulled cross-account. In order to grant you access to these images, notify Axia and provide your AWS Account ID.

AWS prerequisites

  • A dedicated AWS account for this deployment (each environment = its own account).
  • Admin access for the one-time bootstrap, then the scoped deployment role for applies.
  • Bedrock model access enabled in the region for the Claude models used by llm-service and chat-service.
  • Pick one region and use it consistently across the whole deployment.

Data-source credentials (collect before deploy)

  • Microsoft Purview DLP: an Entra app with Graph SecurityAlert.Read.All (can reuse the Outlook app). Full steps in §8.1.
  • Cursor (user-prompt events): captured via Cursor's local beforeSubmitPrompt hook deployed to developer endpoints, forwarding to the webhook receiver — you set a webhook source secret. Fleet-wide deployment needs Cursor Enterprise. See §8.2.

  • SMTP (optional reviewer-alert email): host / port / user / password / from-address.

03 Phase 0 — AWS account bootstrap

One-time, with admin credentials. Creates the Terraform state backend that Terraform assumes.

Set your context

bash
cd axia-deploy-<version>/
export AWS_REGION=<your-region>
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
echo "Deploying to account ${ACCOUNT_ID} in ${AWS_REGION}"

Create the Terraform state backend (S3 + DynamoDB lock)

bash
cd terraform/init
aws cloudformation create-stack \
  --stack-name terraform-backend \
  --template-body file://terraform-backend.yaml \
  --region ${AWS_REGION}

# confirm
aws cloudformation describe-stacks --stack-name terraform-backend \
  --region ${AWS_REGION} --query 'Stacks[0].StackStatus'

Yields the state bucket by convention: terraform-state-<ACCOUNT_ID>-<REGION>, versioned with public access blocked.

04 Phase 1 — Terraform infrastructure

Apply the stacks in order: terraform/vpc/ (optional) → terraform/platform/. Skip terraform/vpc/ if you want to use your existing VPC and subnets instead (see below). Backend convention for every stack: bucket terraform-state-<ACCOUNT_ID>-<REGION>, key <REGION>/<stack>/terraform.tfstate.

Per-environment config files

Both terraform/vpc and terraform/platform ship a terraform.tfvars.example and a backend.hcl.example, with ${ACCOUNT_ID} / ${AWS_REGION} placeholders. Expand them into the real terraform.tfvars / backend.hcl files with envsubst (recommended), or copy the .example files by hand and fill in the placeholders yourself. Terraform loads a file named terraform.tfvars automatically, so plan/apply don't need a -var-file flag once it exists:

bash
cat terraform.tfvars.example | envsubst > terraform.tfvars
cat backend.hcl.example      | envsubst > backend.hcl

Run this from inside each stack's directory, right before applying it — see below (terraform/vpc, then terraform/platform).

Apply the VPC stack (optional)

Creates 10.0.0.0/16 with 3 public + 3 private /20 subnets across 3 AZs and a NAT gateway. These are defaults — change vpc_cidr, public_subnet_cidrs, and private_subnet_cidrs in terraform.tfvars if you need different ranges. Its output is consumed by the platform stack via remote state. Skip this if you're using an existing VPC.

bash
cd ../vpc     # axia-deploy/terraform/vpc
export AWS_REGION=<your-region>
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
cat terraform.tfvars.example | envsubst > terraform.tfvars
cat backend.hcl.example      | envsubst > backend.hcl

terraform init -backend-config=backend.hcl
terraform plan
terraform apply

Apply the platform stack

Reads the VPC remote state and creates: the Platform EC2 (t3a.large, Ubuntu 22.04, gp3 100 GB encrypted, private subnet, Docker bootstrapped by user_data.sh), the Classifier EC2, the DocumentDB cluster (master docdbadmin, password auto-managed in Secrets Manager, TLS + encryption + 7-day backups + deletion protection), the S3 content-store bucket and access user, all IAM roles/policies, and CloudWatch log groups.

bash
cd ../platform     # axia-deploy/terraform/platform
export AWS_REGION=<your-region>
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
cat terraform.tfvars.example | envsubst > terraform.tfvars
cat backend.hcl.example      | envsubst > backend.hcl

In the generated terraform.tfvars, fill in roles_allowed_to_assume_platform_role — SSO/admin role names in THIS account allowed to assume the platform EC2 role.

Using an existing VPC

If you skipped terraform/vpc/: leave vpc_state_key empty (""), set vpc_name to the Name tag on the existing VPC, and set private_subnet_ids / public_subnet_ids to the existing subnet IDs.

Other platform variables: project_name (platform, drives resource names + EC2 Name tag), documentdb_instance_class (db.t3.medium), documentdb_instance_count (1), documentdb_engine_version (8.0.0), classifier_instance_type (c7i-flex.4xlarge), classifier_volume_size (200 GB), and — set enable_alerts = true to also set alerts_email + alerts_client_name.

bash
terraform init -backend-config=backend.hcl
terraform plan
terraform apply

Capture the outputs you need for the app layer:

bash · terraform output
terraform output ssm_command                        # connect to platform host
terraform output documentdb_cluster_endpoint
terraform output documentdb_get_password_command
terraform output content_store_bucket_name
terraform output s3_content_access_get_credentials_command
terraform output classifier_ssm_command             # connect to ML host

05 Phase 2 — Deploy the application layer

The application is delivered onto the EC2 host as a docker-compose stack: generate config from TF outputs, copy it and the compose file to the host over SSM, and run the deploy script.

Six files must be present in /var/lib/axia on the host before you deploy:

FileWhere it comes from
deployment-config.jsonGenerated into axia-deploy/configs/ by scripts/generate-deployment-config.sh (below).
config.envCopy configs/platform/config.env.example and fill in the per-client values (below).
docker-compose.ymlBundled at compose/platform/docker-compose.yml.
deploy-v2.shBundled at scripts/deploy-v2.sh; run it from /var/lib/axia on the host (below).
fluent-bit-cloudwatch.confBundled at configs/fluent-bit-cloudwatch.conf. Fluent Bit config for the log-shipping sidecar: tails every container's Docker log, reassembles multi-line stack traces into single records, and ships each service's logs to its own CloudWatch stream.
extract_service.luaBundled at configs/extract_service.lua. Lua filter the config above calls to derive each container's service name from its com.docker.compose.service label, so CloudWatch streams are named per-service rather than by container ID.

Generate the deployment config

bash
cd ../../scripts     # axia-deploy/scripts
./generate-deployment-config.sh

It reads terraform output (from terraform/platform), fetches the DocumentDB password from Secrets Manager and S3 credentials from SSM, URL-encodes the password, and writes configs/deployment-config.json (account, region, ECR registry/region, DocumentDB endpoint, full TLS mongodb_uri, content-store bucket + region, S3 access/secret keys, S3 URL).

Pre-configured

The script resolves the platform stack relative to itself (../terraform/platform) — no path editing required. The ECR registry/region in the output point at the Axia ECR account by design (that is where images are pulled from cross-account).

Create config.env

Copy configs/platform/config.env.example to config.env and fill in the per-client, non-generated values (the data-source credentials from §2). Leave a connector's section commented if you are not enabling it.

Copy files to the host and deploy

bash
cd ../terraform/platform     # axia-deploy/terraform/platform
$(terraform output -raw ssm_command)   # aws ssm start-session --target i-xxxx …

Place these six files in /var/lib/axia on the host — the deploy script requires all six:

  • deployment-config.json (from above)
  • config.env
  • docker-compose.yml — the bundled compose/platform/docker-compose.yml
  • deploy-v2.sh — the bundled deploy script
  • fluent-bit-cloudwatch.conf — bundled at configs/fluent-bit-cloudwatch.conf
  • extract_service.lua — bundled at configs/extract_service.lua

Then run the deploy script on the host:

bash
cd /var/lib/axia     # on the EC2 host
./deploy-v2.sh
docker compose ps

It installs jq/python3 if missing, downloads the DocumentDB CA bundle to /var/lib/axia/certs/global-bundle.pem, logs Docker in to ECR, generates /var/lib/axia/.env (mapping config → service env keys, fanning the Mongo URI to the services, setting the Bedrock LLM_MODEL, KAFKA_BOOTSTRAP_SERVERS=kafka:29092, and the S3/bucket vars) and appends your entire config.env, then runs docker compose pull and up -d.

The script is idempotent — safe to re-run for upgrades.

08 Data-source integrations

Axia ingests external events through connectors. This section covers the two integrations for this deployment: Microsoft Purview DLP (Axia polls Microsoft Graph outbound) and Cursor user-prompt events (forwarded to Axia's webhook receiver by a hook on each developer's machine). Both are additive — configure only what you use. All values below go in config.env (§5.2).

8.1 · Microsoft Purview DLP

How it works. The connector-purview service (the shared connector image with CONNECTOR_TYPE=purview) authenticates to Microsoft with the OAuth2 client-credentials flow and polls the Microsoft Graph Security API for DLP alerts. Each alert is published to the dlp.events Kafka topic, where the existing enrichment-worker-dlp consumes it. The connector reaches out to Microsoft — no inbound network exposure is needed.

microsoft graph
GET https://graph.microsoft.com/v1.0/security/alerts_v2
    ?$filter=serviceSource eq 'dataLossPrevention'
# incremental polls add:  and lastUpdateDateTime gt <timestamp>
# results are paged via @odata.nextLink
Purview-side prerequisites

DLP policies must be configured and enabled in the Microsoft Purview portal with rules set to generate alerts (no policies → no alerts). Single-event alerts work on any DLP subscription; aggregated/threshold alerts require E5 / the Purview compliance tier. New or modified policies can take up to ~3 hours to start generating alerts.

Azure Entra app registration (one-time, in the customer tenant):

  1. Entra admin center → App registrations → New registration. Name it (e.g. "Axia Purview DLP Connector"), single-tenant, no redirect URI. Register.
  2. On Overview, copy Application (client) ID → MICROSOFT_CLIENT_ID and Directory (tenant) ID → MICROSOFT_TENANT_ID.
  3. Certificates & secrets → New client secret → copy the Value (shown once) → MICROSOFT_CLIENT_SECRET.
  4. API permissions → Add a permission → Microsoft Graph → Application permissions → add SecurityAlert.Read.All.
  5. Grant admin consent for the tenant — required, or the token won't carry the permission.
Reuse the Outlook app

You can reuse the same Entra app as the Outlook connector: just add the SecurityAlert.Read.All permission to it and reuse the same tenant/client/secret.

Configure the connector (config.env):

config.env · purview
MICROSOFT_TENANT_ID=<tenant-id>
MICROSOFT_CLIENT_ID=<client-id>
MICROSOFT_CLIENT_SECRET=<client-secret>
PURVIEW_START_DATE=            # optional backfill (e.g. 2026-01-01); blank = from now

Stack-provided defaults you normally leave alone: MICROSOFT_GRAPH_BASE_URL=https://graph.microsoft.com/v1.0, MICROSOFT_AUTHORITY_BASE_URL=https://login.microsoftonline.com, PURVIEW_PENDING_QUEUE_NAME=dlp.events.

Verify. docker compose logs -f connector-purview shows a successful token fetch and poll; DLP alerts land on the dlp.events topic (visible in kafka-ui) and flow through enrichment-worker-dlp into the events service.

Microsoft references: list alerts_v2 · serviceSource enum · client-credentials / .default · DLP alerts prerequisites & licensing.

8.2 · Cursor (user-prompt events)

We ingest only the user-prompt events — the text developers submit to Cursor's AI — for sensitive-data detection.

How it works. Unlike Purview, you don't point Cursor at a URL — Cursor has no cloud-side webhook or API that emits user prompts (its only outbound webhook is Cloud-Agent status; its Admin API, audit logs, and code-tracking exports all exclude prompt text). Prompt capture is done with a local Cursor hook — beforeSubmitPrompt — that runs a small script on each developer's machine right after the user hits send; the script receives the prompt as JSON on stdin and forwards it to Axia's webhook receiver. Because your script makes the call (not Cursor's cloud), it sets the static X-Webhook-Secret header itself, so it's directly compatible with the receiver — no HMAC shim. Enabling only user-prompt events means declaring only the beforeSubmitPrompt hook.

flow
Developer's Cursor ──beforeSubmitPrompt hook──▶ forwarder script ──HTTPS POST──▶ webhook-connector :8011
   (prompt text)                                (adds X-Webhook-Secret)          POST /api/v1/webhooks/cursor
                                                                                 → enrichment.pending
                                                                                 → enrichment-worker-webhook

Step 1 — register the source on the Axia side (config.env):

config.env · webhook source
# name:secret pairs, ';'-separated (this is the static X-Webhook-Secret value)
WEBHOOK_ENRICHMENT_SOURCES=cursor:<axia-webhook-secret>
WEBHOOK_ENRICHMENT_TOPIC=enrichment.pending

Step 2 — expose the receiver to developer machines. The receiver (:8011) sits on the private-subnet platform host, so front it with an HTTPS ingress (ALB / reverse proxy) reachable from where developers run Cursor (corporate network / VPN, or internet for remote staff). Terminate TLS at the ingress; forward POST /api/v1/webhooks/cursor.

Step 3 — deploy the Cursor hook to developer endpoints. Add a hooks.json plus a forwarder script. Scope options: ~/.cursor/hooks.json (per user), <project>/.cursor/hooks.json (per repo, committable), or Enterprise-managed hooks pushed from the Cursor team dashboard / MDM for tamper-resistant fleet-wide rollout.

hooks.json — declare only the prompt hook
{
  "version": 1,
  "hooks": {
    "beforeSubmitPrompt": [{ "command": ".cursor/hooks/forward-prompt.sh" }]
  }
}
forward-prompt.sh
#!/usr/bin/env bash
payload="$(cat)"                                   # beforeSubmitPrompt event on stdin
gen_id="$(printf '%s' "$payload" | jq -r '.generation_id // empty')"
curl -s -X POST "https://<ingress-host>/api/v1/webhooks/cursor" \
  -H "Content-Type: application/json" \
  -H "X-Webhook-Secret: <axia-webhook-secret>" \
  -H "X-Idempotency-Key: ${gen_id}" \
  --data "$payload" >/dev/null
echo '{"continue": true}'    # allow the prompt; leave failClosed off so errors never block

Payload & idempotency. The beforeSubmitPrompt event carries prompt (the text), user_email, conversation_id, generation_id, attachments[], workspace_roots[], hook_event_name. There is no timestamp (stamp on receipt) and no id/event_id field — pass generation_id as X-Idempotency-Key (as above) so the receiver dedupes per prompt; conversation_id + generation_id is the stable composite key.

Enablement & privacy

Central config & enforcement via MDM. Deploy and enforce the hook fleet-wide with your MDM (and/or Cursor Enterprise managed hooks from the team dashboard) so it is applied consistently and developers cannot remove or bypass it. Ad-hoc per-repo or per-user hooks.json is fine for testing but is removable by developers. Capturing prompt text is user-input monitoring — handle as a consent/policy matter and align with Cursor Privacy Mode. Leave failClosed off so a forwarder error never blocks a developer.

Verify. Submit a prompt in Cursor; the forwarder POSTs and the receiver returns 202 Accepted {"status":"accepted","source":"cursor",…}; the event appears on enrichment.pending and is processed by enrichment-worker-webhook.

10 Operations

  • Connect to a host: aws ssm start-session --target <instance-id> --region <region> (or terraform output ssm_command). Hosts are in private subnets — no SSH.
  • DocumentDB shell from your laptop: use documentdb_ssm_port_forward_command to map localhost:27017, then connect with a TLS client using the RDS CA bundle (authMechanism=SCRAM-SHA-1).
  • Upgrade a service: update the image tag in .env on the host, then re-run the deploy (docker compose pull && up -d).
  • Logs: docker compose logs -f <service> on the host; container logs also ship to CloudWatch (/platform/services, /ml).
  • Off-hours shutdown: the platform EC2 can be tagged shut-down=true to opt into an off-hours scheduler (optional cost control).

11 Known gotchas & caveats

Read before you deploy

These are the failure modes most likely to bite a first deployment.

  1. Two hosts required. The platform compose file does not include llm-service or the parser — those live on the ML host. Both must run and be wired by private-IP URLs.
  2. DocumentDB, not plain MongoDB. Connections require TLS + the RDS CA bundle at /app/certs/global-bundle.pem and authMechanism=SCRAM-SHA-1. URL-encode the password (scripts/encode-mongodb-password.py).
  3. Bedrock region. llm-service and chat-service need AWS_DEFAULT_REGION set, or they fail with NoRegionError. Verify the model id against aws bedrock list-foundation-models.
  4. The image registry points at Axia's ECR in the generated deployment-config.json by design — that is where images are pulled from cross-account, not your account. The bundled config generator and deploy-v2.sh are already path-fixed and correctly named.
  5. Region consistency. Pin one region across the whole deployment — state bucket, VPC, DocumentDB, S3, and the deployment config — and set it before you apply.
  6. Cross-account ECR trust is Axia-side. The host role grants pull actions, but Axia must add your account to each repository policy.
  7. AMI / user_data drift. The EC2 resources set ignore_changes = [ami, user_data], so Terraform will not replace a running host on AMI updates. Use targeted applies for non-EC2 changes.
  8. Purview alerts can lag. New/modified DLP policies take up to ~3 hours to start generating alerts, and app-only reads require SecurityAlert.Read.All with admin consent — a missing consent looks like "authenticated but zero alerts" (§8.1).
  9. Cursor has no cloud-side prompt events. User prompts are captured only via the local beforeSubmitPrompt hook deployed to each developer endpoint (configure and enforce it via MDM for a tamper-resistant fleet-wide rollout). The hook's forwarder script sets X-Webhook-Secret itself, so no HMAC shim is needed for this path (§8.2). Capturing prompt text is user-input monitoring — treat as a consent/policy matter.
